# 08 Scenario Comparison — Requirements

## Introduction

Comparison puts a baseline simulation run next to one or more alternative runs and reports the differences.
All figures are read from persisted simulation results (spec 07); the comparison computes differences only,
in the backend, with exact decimal arithmetic. Nothing is estimated and nothing is generated by AI.

Comparisons are computed on demand from stored runs and are not persisted: a run is immutable, so the same
pair always yields the same comparison.

## Requirements

### Requirement 1: Comparable runs

**User Story:** As a manager, I want comparisons only between futures that start from the same factory state,
so that differences are caused by my changes and nothing else.

#### Acceptance Criteria

1. WHEN a client sends `POST /api/simulations/compare` with a baseline run id and one to five alternative run ids THE SYSTEM SHALL verify every run exists, belongs to the same factory and is `COMPLETED`.
2. WHEN any run is not `COMPLETED` THE SYSTEM SHALL return 409 naming the run and its status.
3. WHEN an alternative's `fork_at` or `base_state_hash` differs from the baseline's and `allowDifferentBaseline` is not true THE SYSTEM SHALL return 422 with code `DIFFERENT_STARTING_STATE`.
4. WHEN `allowDifferentBaseline` is true and starting states differ THE SYSTEM SHALL return the comparison with `sameStartingState: false` and a warning for each differing run.
5. WHEN runs were produced by different algorithm versions THE SYSTEM SHALL return the comparison with a warning `DIFFERENT_ALGORITHM_VERSION`.
6. WHEN any compared run ended with a termination reason other than `COMPLETED` THE SYSTEM SHALL include a warning `INCOMPLETE_SIMULATION` for that run.

### Requirement 2: Summary differences

**User Story:** As a factory owner, I want to see how each headline metric changes, so that I can judge a
decision at a glance.

#### Acceptance Criteria

1. WHEN a comparison is produced THE SYSTEM SHALL report, for each alternative and each of these metrics, the baseline value, the alternative value, the absolute difference (alternative minus baseline) and the percentage difference: elapsed completion time, processing time, working wait time, throughput, output stones, output carats, total cost, cost per output stone, each cost component, machine utilization, employee utilization, orders completed, orders delayed, on-time delivery rate.
2. WHEN the baseline value is zero or null THE SYSTEM SHALL report the percentage difference as `null`.
3. WHEN either value is null THE SYSTEM SHALL report the absolute difference as `null`.
4. WHEN a metric has a direction in which lower or higher is operationally better THE SYSTEM SHALL include `betterWhen: "LOWER" | "HIGHER"` and `direction: "IMPROVED" | "WORSENED" | "UNCHANGED"`; cost metrics are marked `LOWER`.
5. WHEN utilization metrics are reported THE SYSTEM SHALL give `betterWhen: null` and no direction, because higher utilization is not inherently better.
6. WHEN values are returned THE SYSTEM SHALL label the object `source: "SIMULATED"` and include each metric's unit.

### Requirement 3: Stage and resource differences

**User Story:** As an operations manager, I want to see where in the factory the difference arises, so that I
understand the mechanism.

#### Acceptance Criteria

1. WHEN a comparison is produced THE SYSTEM SHALL report per stage, for the baseline and each alternative: mean working wait, mean queue length, maximum queue length, throughput, limiting pool utilization and bottleneck score, with differences.
2. WHEN a comparison is produced THE SYSTEM SHALL report per resource pool: capacity, utilization, busy and idle unit-seconds and cost, with differences.
3. WHEN a pool or stage exists in one run and not the other THE SYSTEM SHALL include it with the missing side as `null`.

### Requirement 4: Bottleneck change

**User Story:** As a production manager, I want to know whether the bottleneck moved, so that I do not fix
one constraint only to hit the next.

#### Acceptance Criteria

1. WHEN a comparison is produced THE SYSTEM SHALL report for each alternative the baseline's primary bottleneck stage, the alternative's, and a `change` of `SAME`, `MOVED`, `RESOLVED` (baseline had one, alternative has none) or `EMERGED` (baseline had none, alternative has one), or `NONE` when neither has one.
2. WHEN the bottleneck moved THE SYSTEM SHALL include both stages' scores in both runs.

### Requirement 5: Order delivery differences

**User Story:** As a planner, I want to see which orders finish earlier or later, so that I can tell
customers what to expect.

#### Acceptance Criteria

1. WHEN a comparison is produced THE SYSTEM SHALL report per order present in both runs: due time, completion time in each run, the difference in seconds and the outcome in each run.
2. WHEN an order is unfinished in a run THE SYSTEM SHALL report its completion time as `null` and the difference as `null`.

### Requirement 6: Applied changes

**User Story:** As a reader of a comparison, I want to see what was changed in each alternative, so that
cause and effect are on the same page.

#### Acceptance Criteria

1. WHEN a comparison is produced THE SYSTEM SHALL include, for each run, the scenario name and the list of applied changes taken from that run's stored snapshot (not from the scenario's current changes).

### Requirement 7: Scenario comparisons

**User Story:** As a user on a scenario's page, I want its latest result compared with the baseline
automatically, so that I do not have to pick runs by hand.

#### Acceptance Criteria

1. WHEN a client sends `GET /api/scenarios/{id}/comparisons` THE SYSTEM SHALL compare the scenario's latest `COMPLETED` run with the latest `COMPLETED` run of every baseline scenario (no changes) of the same factory that has the same `base_state_hash`.
2. WHEN no such baseline run exists THE SYSTEM SHALL return an empty list and `baselineMissing: true`, with the id of a baseline scenario at the same fork timestamp if one exists and has not been run.
3. WHEN the scenario has no `COMPLETED` run THE SYSTEM SHALL return an empty list.

### Requirement 8: Actual outcome reference

**User Story:** As a user who branched from the past, I want to see what actually happened after the fork
next to the simulated futures, so that I can judge how realistic the baseline is.

#### Acceptance Criteria

1. WHEN `includeActual=true` and recorded history exists after the fork timestamp THE SYSTEM SHALL include an `actual` block with, for the orders present in the baseline run: number completed by the latest recorded event, their recorded completion times, and output stones and carats recorded at the final stage, labelled `source: "ACTUAL"` with `asOf` set to the last recorded event time.
2. WHEN the actual block is returned THE SYSTEM SHALL NOT compute differences between actual and simulated values in the summary table; the two are shown side by side only, because recorded history is truncated at `asOf` while the simulation runs to completion.
